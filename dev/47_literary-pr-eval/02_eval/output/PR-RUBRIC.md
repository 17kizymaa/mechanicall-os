# PR scorecard — derived from literary `14` + GPT-56 `09`/`10`/`13`

**Not law.** Use when reading a GitHub PR or a local branch. Human merges. Models do not `aether approve`.

Center test: **Does this change make authority more inspectable, or does it make a capability look like consent?**

Score each row: **PASS / FAIL / N/A**. One FAIL in blockers is enough for “do not merge as distribution.” Lab merge may still be honest if the PR *says* lab.

## Blockers (GPT-56 already used these)

| # | Question | Literary clause | Fail looks like |
|---|----------|-----------------|-----------------|
| B1 | Are `approve` / `reject` / `next` still human-only in code and in events? | Human confers authority | Tests or agents emit `by:human`. MCP tool named `approve`. |
| B2 | Does Decide/Publish work on the claimed surface without a hidden POSIX `aether`? | Capability ≠ authority | Stock-phone Yes shells out to missing `bin/aether`. |
| B3 | Can transport write outside the bound tree? | Refusal; bind ≠ operator repo | Zip slip, symlink, absolute members, MCP roots that include `/`. |
| B4 | Is live CURRENT excluded, or honestly applied by a human? | One Next; proposal ≠ instruction | PR ships a new CURRENT as if Yes happened. |
| B5 | If it claims distribution: is there a built artifact + a walk, not string-search 10/10? | Receipts are part of the action | Green CI, no APK/AAB, no emulator bind→decide. |
| B6 | If it claims off-LAN: is the receipt actually LTE/Play, not USB-on-mbp-edge? | Receipts | `adb` on edge sold as testers. |

## How to write the review comment

1. One-line verdict: lab-ok / not-distribution / blocker.
2. Blockers table with file:line.
3. What to preserve (the walk).
4. What the PR is *not* authorized to be (production, LTE, Yes).
